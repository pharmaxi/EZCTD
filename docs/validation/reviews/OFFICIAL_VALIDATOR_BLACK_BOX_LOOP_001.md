## 1. 结论

“官方验证器黑盒观察仍然是 0”已经不再成立。

当前经入场条件判定并保存原生证据的观察为：

| 计数 | 当前值 |
|---|---:|
| 官方二进制黑盒观察 | **3** |
| 环境适配型官方观察 | **3** |
| 原始运行环境等价观察 | **0** |
| 可用于规则校准的观察 | **0** |

三次观察均使用同一份经哈希固定的官方应用字节、同一冻结空目录输入、独立安装运行时和相同出站阻断条件。三次均完成：

1. 选择申报资料目录；
2. 选择报告输出目录；
3. 点击“启动验证”；
4. 捕获官方程序原生终态；
5. 取得官方程序生成的原生 HTML 报告；
6. 复核输入目录前后字节清单不变；
7. 保存截图、UI 操作轨迹、进程证据、防火墙证据和原生报告；
8. 通过 8 项入场门槛。

三次官方终态均为“执行成功”。三份原生报告均显示：

```text

警告：22
错误：96
可见规则条目：151
```

原始 HTML 的 SHA-256 不同，这是因为报告内嵌执行时间；剔除执行时间、生成报告名、绝对本地路径和纯展示性 SVG 后，三次的规范化全文摘要和结构化语义摘要完全一致。

机器可读稳定性证据：

`evidence/regulatory/snapshots/cde-validator-v1.1.0/black-box-stability/cn-v11-probe-000-invalid-empty-root-three-run-stability.json`

## 2. 为什么此前一直是 0

此前不是“软件已经准备好，只差点击运行”，而是连续存在四个不同层级的问题。

### 2.1 官方二进制并未真正取得

旧证据目录仍是：

```text
UNRESOLVED_NO_CONFIRMED_VALIDATOR_ASSET
```

旧采集脚本点击 CDE 专栏中的一级“eCTD验证软件”后，直接等待文件出现；但页面实际行为是打开二级下载弹窗，因此网络候选为空：

```text
candidates=[]
```

这意味着此前关于“验证器已从官方专栏取得并完成静态检查”的表述过早，必须撤回。

### 2.2 `downloadFiles(4/5)` 不是下载动作

浏览器诊断探针保存了：

- `downloadFiles` 实际函数体；
- 弹窗前后 DOM；
- 二级控件；
- 浏览器网络事件；
- 同源 JavaScript；
- 页面截图。

由此确认：

```text
downloadFiles(4) → 打开验证软件二级弹窗
downloadFiles(5) → 打开操作手册二级弹窗
```

真正下载路径位于弹窗中。采集器随后改为解析当前同源 JavaScript 和二级控件，而不是猜测 URL。

### 2.3 官方程序在托管 Windows 上存在文件名编码问题

官方安装后的 `eCTD验证软件.exe` 在 GitHub 托管的非中文 Windows 环境中未能稳定显示 JavaFX 主界面。取证表明这与 Launch4j 启动路径/文件名编码有关。

解决方式不是修改二进制，而是在同一 NTFS 卷建立：

```text
CDEValidator.exe
```

它是官方 EXE 的字节完全相同硬链接：

- 相同 SHA-256；
- `samefile=true`；
- 没有补丁、注入、反编译或私有 API 调用。

因此当前观察只能称为：

```text
ADMISSIBLE_ENVIRONMENT_ADAPTED_OFFICIAL_OBSERVATION
```

不能称为原始运行环境等价。

### 2.4 JavaFX UIA 控件对象会失效

第二版事务已经能看到 JavaFX 控件，但在调用 `InvokePattern` 时出现 UIA/COM 对象失效。问题不是验证器拒绝输入，而是自动化层缓存了过期控件对象。

第三版只改变交互传输：

- 每次操作前重新枚举主窗口；
- 重新定位目标控件；
- 读取当前屏幕矩形；
- 将窗口置前；
- 在当前可见矩形内发送物理坐标点击；
- 保存每次点击坐标和矩形。

没有同时更换输入、验证标准或应用字节，因此成功可以归因于 UI 传输修复。

## 4. 新增的报告解析器

新增：

```text
tools/regulatory/parse_cde_validator_native_report.py
```

它同时输出三种不同的身份：

1. **原始字节 SHA-256**：用于证明某一次原生报告的来源和完整性；
2. **规范化可见文本摘要**：剔除时间、报告文件名、绝对路径和展示标记；
3. **结构化语义摘要**：验证标准、章节统计、规则编号、严重程度、规则文本和详情。

不能因为原始 HTML 的时间字段不同，就把稳定运行错误判定为不一致；也不能只比较“错误总数相同”便声称规则结果相同。两层摘要共同约束这两个方向的误判。

聚焦测试：

```text
tests/regulatory/test_parse_cde_validator_native_report.py
```

测试覆盖：

- 执行时间和报告名变化时，原始字节哈希应变化；
- 同一语义结果的规范化摘要必须相同；
- 章节总数、规则编号、严重程度和详情应正确提取。

## 5. 自我审核：哪些结论仍然不能说

### 5.1 不能说“官方验证器兼容性已经证明”

当前输入是空目录。官方程序能够运行、产生原生报告且结果可重复，只证明事务管道可靠，不证明 EZCTD 生成物可提交。

### 5.2 不能说“PDF 规则已经校准”

当前报告中的 96 条错误主要是缺少 `index.xml`、`cn-regional.xml`、模块目录和其他骨架内容。没有单变量 PDF 变异，无法将某条消息归因到具体 detector。

因此：

```text
calibration_informative_observations = 0
```

保持不变是正确的。

### 5.3 不能说“托管 Windows 等同于申报人的普通中文 Windows”

当前必须使用字节相同的 ASCII 硬链接别名才能进入 UI。该适配不改变官方程序字节，但它仍然是环境适配。

```text
stock_environment_official_observations = 0
```

仍然正确。

### 5.4 不能忽略 `0000` 路径警告

每次选择 `C:/EZCTDProbeInput/0000` 后，官方程序均显示：

```text
不规范的资料路径
序列文件夹不是数字。仍要使用？
```

点击确认后，程序确实继续验证、生成完整 HTML 报告并显示“执行成功”，所以本次不是“只捕获了前置弹窗”。但该提示与表面的四位数字目录不一致，必须隔离验证：

```text
同一空目录，仅把 0000 改成 0001
```

在这一问题解释清楚前，不能把路径警告当作无关噪声。

## 6. 对状态模型的修正

此前汇总器只读取事务末尾写入的 `admissibility`。一旦 UI 中途失败，已经通过的二进制身份、输入身份和防火墙门槛也会被错误显示为失败。

现已改为：

```text
PASS
FAIL
NOT_REACHED
```

三态记录。

例如 UI 尚未点到验证按钮时：

- 二进制身份可以是 PASS；
- 防火墙可以是 PASS；
- 原生终态应是 NOT_REACHED；
- 不应把前三项全部归零。

计数规则仍然严格：只有全部强制门槛通过时，官方黑盒观察才加 1。

## 7. 下一轮 Agent Loop

### A. 先隔离路径警告

建立 `0001` 空目录用例，只改变目录名。观察：

- 是否仍出现“序列文件夹不是数字”；
- 原生报告中的序列识别是否变化；
- 5/22/96 与 151 条可见规则是否变化。

### B. 再建立最小 V1.1 序列基线

由已经固定的 V1.1 技术附件包生成：

- 正确序列目录；
- `index.xml`；
- `cn-regional.xml`；
- 官方 `util` 文件；
- 最小 Module 1 中国区域结构；
- 一个确定性 PDF 叶节点。

目标不是一开始追求“零错误”，而是先消除与 PDF 变异无关的大量结构错误，并形成可重复基线。

### C. 执行单变量校准

建议顺序：

```text
baseline-pre
→ 6.8 承前缩放变异
→ baseline-mid
→ 6.22 Fast Web View 变异
→ 6.26 未嵌入字体变异
→ 6.19 安全设置变异
→ 6.21 密码保护变异
→ 6.1 损坏/不可读 PDF 变异
→ baseline-post
```

每个变异必须保留：

- 输入包摘要；
- 原始官方报告；
- 结构化语义摘要；
- 新增/消失的规则消息；
- 严重程度；
- 前后基线稳定性；
- detector 预期与官方结果的差异。

### D. 单独验证原始环境等价

使用中文系统区域设置的自托管或一次性 Windows VM，以原始中文文件名启动，不使用 ASCII 别名。该结果单独计入 stock-environment parity，不能与当前三次适配型观察混算。

## 8. 当前阶段判断

本轮已经解决的是：

```text
官方来源 → 二进制身份 → 安装 → 启动 → UI 交互 → 输入/输出选择
→ 启动验证 → 原生终态 → 原生报告 → 前后输入保真 → 可重复运行
```

尚未解决的是：

```text
最小有效序列 → 干净基线 → 单变量 PDF 变异 → 官方消息映射
→ detector 灵敏度/特异度 → 原始中文环境等价
```

因此，本轮结果是实质性突破，但不是“验证器问题全部解决”。
