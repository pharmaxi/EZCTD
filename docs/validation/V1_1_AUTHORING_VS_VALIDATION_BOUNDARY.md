# eCTD V3.2.2/V1.1：PDF 制作要求与验证消息边界

> 状态：现行正式来源已核验。本文用于防止 EZCTD 将《eCTD技术规范V1.1》的制作要求、建议和《eCTD验证标准V1.1》第 6 章消息混为一类。

## 1. 四类依据必须分开

| 类别 | 典型来源 | 可否产生官方第 6 章消息 | EZCTD 默认行为 |
|---|---|---:|---|
| 官方验证规则 | 《eCTD验证标准V1.1》6.1–6.26 | 是 | 按正式严重程度报告，并等待官方验证器校准 |
| 官方制作要求 | 《eCTD技术规范V1.1》3.4、3.5 | 否，除非明确映射到验证标准 | 单独显示“制作要求”，不得伪装成官方错误代码 |
| 官方建议 | 技术规范中“建议”类表述 | 否 | 非阻断建议，保留原始措辞和来源 |
| 产品安全护栏 | EZCTD 自身 | 否 | 单独显示产品风险，不修改官方严重程度 |

机器可读来源：

`rulepacks/cn-cde-ectd/v1.1/authoring-guidance.json`

## 2. 与 PDF 产品直接相关的制作要求

### 2.1 导航

除外文参考资料、参考文献和申请表之外，单个申报资料文件超过 5 页，需要使用目录和书签辅助导航。该要求与验证规则 6.23 有直接对应关系；但“目录是否完整、表格与图表目录是否足够”不能仅由“是否存在书签”替代。

当目录和书签不足以完成导航时，可使用超文本链接。跨文档链接至少涉及：

1. 模块一上市后变更或研究等项目至模块二至模块五相应内容；
2. 模块二概述和总结至模块三至模块五详细内容；
3. 临床研究报告至相应附件、表格和图表；
4. PDF 格式临床数据集数据说明文件至相应 XPT 文件。

不得创建跨申请超文本链接。上述要求意味着未来链接检查器必须基于完整申报包和业务节点图，而不能只在单个 PDF 中判断“链接存在/不存在”。

### 2.2 中文字体与字号

技术规范对中文资料给出明确制作要求：

- 字体使用宋体；
- 正文不小于小四号字；
- 表格不小于五号字；
- 目录使用小四号字；
- 脚注使用五号字。

这些要求不应直接转写为第 6 章官方验证消息。PDF 中的子集字体名称、文本矩阵、替代字体和图像文字会使自动判断存在不确定性；更可靠的实现位置是 Word/源文档预检。PDF 阶段只能提供带置信度的制作检查。

### 2.3 颜色与链接可见性

- 叙述性文字使用黑色；
- 超文本链接建议使用蓝色文字，或者黑色文字带蓝色框。

后者是建议，不能成为阻断性 finding。修改链接文字颜色通常需要改写页面内容流，风险远高于设置链接注释边框，因而不属于首批安全自动修复。

### 2.4 外文参考资料

外文资料应配套中文资料，译文与原文一致；在 eCTD 骨架中，外文参考资料与对应中文资料置于同一目录元素下的不同叶元素，中文资料在前。

EZCTD 可以检查语言元数据、兄弟叶节点关系和顺序，但不能凭 PDF 结构自动判断翻译内容一致性。

## 3. 产品实现规则

1. Finding 必须含 `basis_type`：`official_validation_rule`、`official_authoring_requirement`、`official_recommendation` 或 `product_guardrail`。
2. 只有正式验证规则可以使用官方消息代码和严重程度。
3. 制作要求即使措辞为“应/需”，也不能自动映射为第 6 章错误；必须先有正式规则映射。
4. “建议”不得在 UI 中显示为错误或阻断项。
5. 链接存在性、链接目标业务合理性和 PDF 链接结构有效性是三个不同问题，分别检查。
6. 字体、字号和颜色优先在源文档阶段检查；PDF 阶段的判断必须显示不确定性和限制。
7. v4.0 征求意见稿中的 baseline 类型例外不得回流至当前 V1.1 制作或验证规则。

## 4. 当前开发影响

P0-B1 只读观察器继续以 6.1–6.26 为官方消息目录。`authoring-guidance.json` 暂不驱动阻断性扫描，仅用于：

- PRD 修订；
- 后续 Word Sharper/源文件预检规划；
- 链接图和资料包上下文设计；
- UI 中“验证问题”与“制作建议”的分栏；
- 未来使用真实资料验证制作质量检查的灵敏度和误报率。
