# CDE eCTD 验证软件：黑盒观察计数与证据标准

> 目的：明确什么情况下 `official_black_box_observations` 才能从 0 增加，防止把“下载成功”“静态检查”“进程启动”或“出现窗口”误算为官方验证结果。

## 1. 一条可采信黑盒观察是什么

一条观察对应一次完整且可复核的事务：

```text
固定验证器字节
→ 固定唯一输入
→ 实际触发验证
→ 观察到终态
→ 保存原生结果
→ 证明输入未被悄然改变
→ 固定完整证据
```

以下条件必须同时满足：

1. **验证器身份确定**
   - 官方下载入口可追溯；
   - 外层 ZIP、安装器和实际应用入口的 SHA-256 全部匹配冻结值；
   - 记录应用文件版本、运行环境和入口路径。
2. **输入身份确定**
   - 仅使用公开或合成资料，不使用真实申报资料；
   - 保存输入目录清单、每个文件 SHA-256、总清单哈希；
   - 每次运行只绑定一个 `case_id` 和一个输入快照。
3. **验证确实被触发**
   - 不能只启动程序；
   - 必须有 UI Automation 动作记录、控件信息或等强度的原生证据，证明已选择输入并执行“验证”。
4. **运行到可解释终态**
   - 成功完成、完成并发现问题、输入拒绝或应用明确报错均可；
   - 超时、进程无响应、程序未打开、控件未找到不算完成验证。
5. **原生结果被保存**
   - 优先保存软件生成的原生验证报告；
   - 若首轮输入在导入阶段被拒绝且不会生成报告，可保存完整错误对话框/UI Automation 树、截图、窗口标题和进程日志，但必须能唯一确定软件给出的结果；
   - 仅凭脚本自己的推测或退出码不够。
6. **输入保真**
   - 运行前后输入清单哈希一致；
   - 如软件会写入输入目录，必须隔离到副本并明确记录新增、删除和修改文件。
7. **证据完整**
   - 保存原始 JSON、截图、UI Automation 导出、进程与窗口时间线、原生报告、输入清单和 Actions artifact digest；
   - Git 只保存边界清晰的结构化摘要，原始二进制和大体积证据放 Actions artifact。

只有上述七项全部通过，才执行：

```text
completed_validation_runs += 1
admissible_black_box_observations += 1
official_black_box_observations += 1
```

## 2. 计数器含义

| 计数器 | 增加条件 | 不能由什么触发 |
|---|---|---|
| `launch_reconnaissance_runs` | 官方应用被受控启动并完成进程/窗口/UI 观察 | 下载或静态检查 |
| `completed_validation_runs` | 已触发验证并达到可解释终态 | 仅启动应用、超时、脚本异常 |
| `admissible_black_box_observations` | 完成验证且证据满足本文件七项条件 | 无原生结果、输入身份不明 |
| `calibration_informative_observations` | 可采信观察还能唯一对应预期规则或预期行为 | 空输入、复合缺陷、无法定位消息来源 |
| `repeated_baseline_controls` | 同一 clean baseline 在相同条件下重复并可比较 | 不同输入或不同版本运行 |
| `official_black_box_observations` | 与 `admissible_black_box_observations` 同步；保留作为对外总计 | 人工估计、静态分析、UI 推断 |

## 3. 第一次观察不必是假装“干净基线”

为了先证明完整通路，第一条观察可以使用一个**确定性、明显无效、完全合成**的输入。例如：

```text
case_id: cn-v11-probe-000-invalid-empty-root
目标：验证软件能够选择目录、执行验证，并给出可保存的原生拒绝或错误结果
预期：不声称对应 6.1–6.26 中某一条具体规则
```

如果证据完整，它可以使：

```text
official_black_box_observations = 1
calibration_informative_observations = 0
```

这比为了追求“漂亮结果”而先手工构造一个未经证明的 clean baseline 更可靠。第一条观察只回答：

> 官方软件是否真正完成了一次可复核的验证事务？

之后再构建最小合法序列和单缺陷变体，进行规则校准。

## 4. 规则校准观察的额外要求

要把一条观察计入 `calibration_informative_observations`，还必须满足：

- 输入只包含一个预设缺陷，或缺陷集合有完整、可证明的依赖说明；
- 预期消息、严重程度和适用条件在运行前冻结；
- 软件原生消息能够稳定映射到预期规则；
- 同一 clean baseline 在变异前后均重复运行，排除缓存或状态污染；
- 记录任何额外消息，不能只挑符合预期的结果。

建议首批顺序：

```text
clean baseline — pre
6.8 承前缩放变异
clean baseline — mid
6.22 Fast Web View 变异
6.26 字体未嵌入变异
6.19 安全设置变异
6.21 密码保护变异
6.1 损坏或不可读 PDF 变异
clean baseline — post
```

## 5. 环境与安全边界

- 官方包当前应用入口没有可依赖的 Authenticode 签名，因此每次运行都必须使用冻结 SHA-256 验证完整哈希链；
- 首轮在 GitHub 托管的临时 Windows runner 中执行，运行前移除仓库凭据并阻断应用出站网络；
- 不执行安装器，使用静态解包得到的固定应用 payload；
- 不允许访问真实申报资料、个人数据、公司内网或长期凭据；
- GitHub 托管 Windows 环境适合探索自动化可行性，但在与官方操作手册要求不一致时，必须明确标记环境代表性限制。
