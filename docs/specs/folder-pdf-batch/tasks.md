# EZCTD · 文件夹PDF批量检查与自动处理｜任务与阶段目标

**规格版本：1.0.0｜编写日期：2026-09-11｜状态：待实施、待产品验证**

仓库：`laojia-a/EZCTD`；本次只读基线：`682217846a49671c9ea8cea441eb7af88b11a161`。本规格不改变当前应用版本`0.3.0.dev0`，不代表新增功能已实现或获CDE认可。[S05]

三件套：`requirements.md`定义做什么与验收条件；`design.md`定义具体实现及操作边界；`tasks.md`定义任务依赖、阶段目标与完成证据。`supporting/traceability.json`是这些规格的结构化索引，不应直接覆盖现有生产规则文件。

## 1. 执行原则与完成定义

当前任务是规格编写；下面全部开发任务均为**TODO**。本轮没有运行新增PDF功能测试、没有修改真实PDF、没有修改或推送GitHub。既有代码可复用，但需要在实施时重新读取HEAD、确认变更并运行相应回归。[S05]

任务按可交付的用户能力拆解，不按“再写一份研究报告”计功能完成。每项完成至少记录：代码提交、真实执行命令、测试/失败/跳过结果、合成输入身份、实际输出和复验、使用引擎及环境、未覆盖范围。用户可见功能还需工作台入口与实际操作证据。

`requirements.md`为需求与验收依据；`design.md`规定边界和操作语义；本文件是有依赖的执行清单。支持范围外可以保留未实现，但必须明确禁止在UI宣称可用，不能以“无法通用处理”代替已承诺有限路径的交付。

## 2. 阶段目标和退出条件

阶段以结果而非日期划分，未掌握实施人员和实測速度前不虚构工期。M3/OCR与M4/字体从M1后并行推进，不等完整导航和格式处理全部完成；M4最终集成需M3接口。M5权限/清理可并行，方向子项依赖M2导航基础。

```text
M0 → M1 ─┬→ M2：书签/链接 ─────────────────┐
         ├→ M3：按需OCR ──┐               │
         ├→ M4：字体诊断/补嵌 ← OCR接口 ──┤→ M6：组合与实际环境交付
         └→ M5：权限/清理/兼容 ───────────┘
```

此图只表达主要分支，任务级精确依赖以下表和结构化索引为准。官方验证器对照不是处理部分临床PDF的启动条件，也不是隐含要求用户补齐XML序列。

### M0 · 基线与规则就位

**用户获得：**将现行6.x、模块范围、材料对照及状态模型固定为可实现输入。

**阶段任务数：**6。**主要前置：**无；开始实施前先读取实际仓库。

**退出条件：**26条规则号/严重程度/例外核对；24项旧号映射齐全；实施前基线测试有实际记录。

**不得冒充完成：**只有文档或JSON不能算产品功能已交付；官网附件字节核实仍须如实记录。

### M1 · 第一个真正可用的文件夹自动处理版本

**用户获得：**一次导入和确认，逐文件检查，自动改初始视图/所选元数据，最后线性化，保留目录输出。

**阶段任务数：**12。**主要前置：**M0。

**退出条件：**M1集成场景实跑；普通文件自动到底；坏文件不阻断；无需改的文件有独立原样副本；原件哈希保持。

**不得冒充完成：**不能以“有26条结果行”宣称所有检查已完成；不把只有CLI函数当UI流程交付。

### M2 · 书签及链接批处理

**用户获得：**承前缩放、路径、动作、目标、目录映射以及输出树最终链接复验可用。

**阶段任务数：**12。**主要前置：**M1。

**退出条件：**6.2—6.15、6.23的P/N/U及IT-11—18实跑；共享目标不会误改；文献默认不强制清理。

**不得冒充完成：**仅简单XYZ通过不能称任意PDF导航全支持；支持矩阵必须明确Fit/命名/远端情况。

### M3 · 按需OCR及复核

**用户获得：**OCR是并行主线：纯扫描及已支持混合页可自动处理，原可见内容保留，疑点集中复核。

**阶段任务数：**8。**主要前置：**M1。

**退出条件：**6.25及IT-19—23实跑；100页只处理需OCR的页；取消恢复有效；数值正确性状态独立。

**不得冒充完成：**输出能搜索不等于转录正确；未支持的低清/手写/复杂混合页不可当成功。

### M4 · 字体诊断与有限精确补嵌

**用户获得：**与OCR并行研究，交付精确匹配的字体补嵌路径及OCR后字体复验。

**阶段任务数：**7。**主要前置：**M1。

**退出条件：**6.26及IT-24—26实跑；至少受支持TrueType和中文CID样本可修复；错字体/缺字体不误成功；最终集成依赖M3的OCR接口。

**不得冒充完成：**只有字体清单或“修复命令执行完毕”不算补嵌交付；不承诺任何第三方PDF都能修复。

### M5 · 权限、内容清理及有限兼容处理

**用户获得：**对凭据授权、附件/注释、动态内容、页面方向和版本建立明确自动处理范围。

**阶段任务数：**9。**主要前置：**M1。

**退出条件：**相关逐规则场景与IT-27—30实跑；任何签名文件不重写；可见内容删除必须有明确批准差异。

**不得冒充完成：**不是通用Acrobat替代；方向子任务依赖M2解析器，其他子任务可并行。

### M6 · 组合运行与实际环境交付

**用户获得：**在目标Windows/NAS环境完成真实用户操作路径验收，冻结可发布能力和限制。

**阶段任务数：**8。**主要前置：**M2, M3, M4, M5。

**退出条件：**IT-31—35实跑、原生及浏览器证据齐全、所有产品级阻断已清；官方对照IT-36单独记录已完成或未完成。

**不得冒充完成：**Win Server CI不等于Win10/11/NAS；本地通过不等于CDE通过，未完成官方对照不可冒充完成。

## 3. 首个可用版本必须交付什么

M1不是“检查器能列出26条”，也不是“单个函数能改视图”。验收时，用户导入一个包含有书签、无书签、无需修改、打不开和存在元数据差异的混合目录；只确认一次；程序自动产出需要修改的PDF以及无需修改的原样副本，并保持原目录结构；失败文件集中列出，原件不变。

M1支持初始视图、可选四说明字段、末端线性化的组合。尚未完成的OCR、字体、复杂导航等明确显示NOT_READY或未判定；不能因这些尚未完成而将整个M1可运行路径长期搁置，也不能提前宣称全26项全部通过。

## 9. 开始实施的顺序

先完成M0的实际基线/模型和上下文，再接M1目录身份、安全输出、内部状态、一次确认管线；视图、说明字段、最终线性化沿用同一修改与复验入口。M1验收时就要看到真实可用的文件夹批处理结果。

M1后立即并行导航、OCR和字体；不要等待合并拆分、XML序列、完整官方发布器等范围外事项。M6产品交付必须列出官方对照任务的实际状态，但它不是强制补齐全申报资料的借口。
