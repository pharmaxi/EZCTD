## 1. 总结与决定建议

项目值得继续，但必须从“为研究验证器不断扩大基础设施”回到“帮助用户可靠地批量检查和修改 PDF”。保留来源研究、PDF 对象分析和官方运行链，暂停通用 Publisher、生命周期、v4.0 继续扩展以及重复工作流的开发。

当前不是成熟产品，也不是零成果：已经有实际代码、26 条规则合同、合成案例设计、固定的官方技术附件和真正的官方程序运行报告；但没有 PDF 规则校准对照，也没有证明可安全接收用户原件的端到端命令行入口。

最重要的新增发现是：当前 CLI 可以把输入 PDF 覆盖为 JSON。此前“原件只读”的原则和对观察器的哈希测试，没有覆盖 CLI 输出边界。本轮使用与远端 blob 完全一致的 CLI 源码、替身解析依赖和临时合成文件，复现同一路径、硬链接别名、符号链接别名三种覆盖，均返回退出码 0。此为真实 CLI 控制流的隔离单元复现，不是完整 PDF 引擎运行。

建议优先顺序：

1. 修复输入保护、包外读取和不完整扫描误报完成的问题；
2. 交付散 PDF 文件夹的只读批量扫描与可读报告；
3. 并行取得一个 PDF 规则的官方正反对照，而非先取得全申报包零错误；
4. 逐功能启用经过验证的低风险副本修复，不把全部 26 条官方校准作为每项功能研发的统一前置条件；
5. 全套官方兼容声明仍须完整验证，不能因缩小研发范围而降低声明标准。

## 3. 产品方向复盘

### 3.1 原始需求不能被替换

用户要的是按照药品申报要求批量处理 PDF。初始入口是电子申报资料制作软件通知，对标产品首要是 PDF Fixer。后续探索 eCTD 是有价值的扩展，却不能自动把总目标改成“生成完整中国 eCTD 序列并通过所有验证”。

建议明确三个使用层次：

- 散 PDF：不要求 XML 包装即可检查版本、密码、字体、书签、链接等可观察属性；上下文不明时单独提示，不编造适用性。
- 普通电子申报资料：另行回源其有效验证标准、目录和索引要求，不把 eCTD 的 26 条自动等同于它的全部要求。
- eCTD：读取骨架、节点、语言和相对路径，提供相应规则解释与官方比较。

共用 PDF 内核，监管配置分别绑定来源。研究一个配置获得的官方证据不应迁移成另一配置的“通过”。普通电子申报制作软件 V1.0.2 通知与 eCTD 技术文件是不同来源对象；本轮没有重新完成普通电子申报全套规则核验。

### 3.2 三种成熟度必须拆开

产品可用性：用户是否能完成目录导入、定位问题、导出副本。

工程可靠性：输入保护、错误隔离、依赖缺失处理、结果完整性、异常文件处理是否可靠。

监管行为校准：在已明确版本和上下文中，特定样本的 EZCTD 结果与官方程序是否一致。

三者互相支持但不互相代替。“Actions success”“26 个分支存在”“官方运行四次”都不是产品完成率。

## 4. 关键发现与处置

### F01 / Critical：报告输出可覆盖输入 PDF

位置：`src/ezctd/cli.py` 的 `main()`，最终直接执行 `args.output.write_text(...)`。

没有检查输入与输出相同，也没有检查不同路径是否指向同一文件。本轮三个隔离实验均显示输入从 `%PDF-` 变成 JSON，且退出码为 0。CLI 源码 Git blob 校验为 `83cfc668889675be12b2b090a6b62422d8657626`，与远端一致。

复现性质：替身只替代 RuleCatalog/PdfContext/Observer，未替代 argparse、路径解析或文件写入。临时测试文件不是用于测试 PDF 解析的有效语料，绝不将该实验算作全 Scanner 集成测试。

处置：在扫描之前校验输出目标；同路径及 samefile 别名必须拒绝；默认禁止覆盖已存在输出；保护全部输入清单而不只保护当前文件；检查父目录符号链接/重解析点；临时输出只在成功校验后提交。单纯字符串不相等或 `resolve()` 不等不足以识别硬链接。高并发时仍应考虑检查与写入之间的竞态。

验收：同路径、相对路径别名、大小写别名、符号链接、硬链接、已存在报告、输出父目录别名、无权限、磁盘写失败；命令结束后全部输入哈希不变。Windows 文件系统情形须本机验证。

### F02 / High：识别出包外目标后仍可能读取它

位置：`pdf_observer.py` 书签/链接遍历与 `_destination_valid()`。

代码先通过 `_relative_target()` 得到 inside 标志并产生问题，但之后构建 `external_file` 时丢弃 inside，随后可调用 `exists()` 和 `pikepdf.open(external_file)`。这使“报告包外链接”和“绝不读取包外文件”脱节。绝对路径也被转换后交给文件读取。本轮为代码审查确认，未在 Windows 上执行 UNC/网络访问实验。

处置：文件解析前实施统一的允许读取根目录，路径越界直接返回 outside_scope；默认不探测任意绝对路径/UNC；只有明确授权且属于同一申请的前序序列可加入读取范围。不要为了判断链接是否坏而读取用户磁盘其他位置。

### F03 / High：6.26 使用 PDF Base-14 代替 CDE 标准字体名单

位置：`BASE14_FONTS`、`_base_font_name()` 以及字体检查循环。

官方 6.26 有自己的标准字体名单，包含宋体、黑体及 Arial、Times New Roman、Courier New 等；代码却豁免 Helvetica、Times-Roman、Courier 等 Base-14 名称。两者不能默认等同。比如裸名 Arial 不在当前集合，Helvetica 却在；这已经是静态策略不匹配，不必等官方黑盒才发现。

不能仅把中文名加进集合就宣称修复完成：需要保留原始 BaseFont、字体程序名称、子集前缀、别名映射来源、嵌入状态和未知状态，之后用真实字体资源样本校准。Form XObject/继承资源中的字体遍历也须补齐。

### F04 / High：局部失败仍可报告 26 条均已检查

位置：`pdf_observer.py` 文本提取异常处理和返回前的 `rules_evaluated`。

文本提取失败时，代码记录 warnings 并置 `texts=[]`；因此可能跳过 6.25 的判定。正常返回前却无条件列出 6.1 至 6.26 全部规则。解析器“打开成功”、规则“实际完成”、规则“没有命中”在数据模型中混在一起。

另有 `_dict_get()`、`_stream_bytes()` 等广泛吞异常辅助函数，可能把无法读取误当成属性缺失。PDFium 的结构探针实际只渲染首末页，不是全页渲染。

处置：逐规则记录 PASS、FAIL、NOT_APPLICABLE、INDETERMINATE、NOT_RUN；缺依赖、读取失败、上下文不足、递归上限、超时都不得按 PASS 计；扫描覆盖信息与官方严重程度分开。缺失上下文可以保守显示候选问题，但必须标为未决，不应伪装成确定适用。

### F05 / High：跨文件命名目的地使用了错误的文档

位置：`_destination_valid(pdf, destination, external_file)`。

函数先在源 PDF 上 `_resolve_named_destination(pdf, destination)`，之后才处理 external_file。远程 GoToR 的命名目的地应在目标文件中解析，当前控制流可能误报“目标不存在”，或错误利用源文件的同名目标。对应缩放检查也使用源 pdf。

处置：先按动作类型选择目标文档，再解析目的地和页面范围；添加“仅目标文件有名称”“两文件同名但指向不同页”“目标缺失”三个正反例。属于静态确认风险，本轮未用真实 pikepdf 集成复现。

### F06 / High：对照包计划与所选规则不相容

原方案选择仿制药首次申请、首次提交，只保留 cn-1-0 说明函，并希望第 1—5 章无阻断。

正式 4.3.3 对该组合列有多个必需元素，只放说明函不满足此要求。XSD 的最小出现次数不能覆盖内容完整性规则。此前“依赖矩阵合法所以一份说明函足够”的推论必须撤回。

同时，说明函 1.0 明确豁免 6.22。将唯一 PDF 放在说明函，再改变线性化去校准 6.22，会得到无信息或误导性结果。

处置：将“验证器读取到 PDF 的研究载体”与“完整申报包合格”拆开。每条校准规则选择已确认适用节点。研究载体中固定的非目标错误可完整保留，但只有当目标 PDF 被明确定位、检查确实运行且不存在阻断/掩蔽时，才可用于限定的差分实验；不得称为合格申报包。

### F07 / High：单变量被误写成所有 XML 字节不变

PDF 改变后，引用它的 leaf checksum 必须更新；被 index.xml 引用的区域骨架如随之变化，也会引发上级 checksum 变化，最后还需按最终 index.xml 字节更新 index-md5.txt。保持 XML 字节完全不变，反而会引入校验和错误。

因此单变量应定义为一个语义处理变量，加上明确列出的依赖性派生变更，而不是所有文件字节不变。验收的是：无额外业务变量、相关校验和一致、无额外页面内容变化、来源和差分可追溯。

上一答将 index-md5.txt 降为候选假设也不准确：正式验证规则 3.15 已有明确要求，技术规范文件表也列出它。未知的应是具体实现兼容性，不是是否存在该要求。

### F08 / Medium：缩放 0 的语义没有正确表示

`_destination_zoom()` 仅将 zoom 为 None 判为 inherit，将 0 判为 explicit。PDF 目的地 XYZ 中 zoom=0 与 null 均表示保留当前缩放；pypdf 的正式 Fit.xyz 文档明确说明这一点。

处置：先纠正 PDF 语义层，分别保留原始编码 0/null；再观察 CDE 对两种编码是否有差异。如果官方软件有特定实现行为，应作为单独的兼容性说明，不覆盖 PDF 标准语义。

### F09 / High：零发现和运行成功没有证明目标规则被执行

四个已计数事务都使用空目录。报告的第 6 章零结果属于空输入现象，不能证明“先通过前五章才会执行第六章”，也不能证明“无需 XML 就不会扫描 PDF”。这些都是待实验假设。

下一实验应先放入可识别的普通 PDF 与一个刻意违规的 PDF，在可解释的上下文中查看官方能否定位目标文件/页。不能不断重复空目录，只增加运行计数。

### F10 / High：状态文件和口头结论发生漂移

本轮 PR 全状态查询返回空数组，与此前“Draft PR #1 持续保留”不一致；不得继续用该旧口头说法。main 和研究分支仍分离，旧 PROJECT_STATUS/P0 路线/P0 自动化快照仍含 0/NOT_RUN，较新的黑盒状态为 4。

当前语料头部明确区分 163 cases、130 implemented recipes、22 specified、11 blocked。不能把 130 和 163 混为同一执行指标，也不能把 implemented 标签当成运行证据。

前文将 latest 的第 3 次 0000 运行称作“首个成功运行”；它的事务 ID 实际为 20260904T024959Z。0001 ZIP SHA-256 实际为 `2dc41a3e927d940f0c1f49191397b0c5132c466278e892ec366e34936148f555`，不是前文的 `3996147...`。

处置：原始证据不改写；用明确更正记录撤回错误说法。一个简短当前状态入口引用不可变运行台账，历史快照注明日期和适用提交。事实状态、实验假设、开发建议分栏。没有原始证据不能以成功标签代替。

### F11 / Medium：自动化扩张快于产品形成

研究分支中存在多个同目的 v1/v2/v3 工作流和修补生成器。多次运行、更多代码行或更多文档不等于更高可靠性。qpdf 与 pikepdf 共享底层，不是两个独立解析器；PDFium 提供了不同渲染实现，但不能自动证明所有文本和导航语义正确。

处置：保留历史，不再为每次小修新增 workflow；明确少数可运行入口。单一标准环境先通过核心测试，再设置 Windows 验证器集成任务。CI 分开报告基础设施运行、测试断言和实验结论。先不要强制合并、删除或重写 191 个研究提交。

## 5. 最小实验设计的重排

Rung 1—6 应是可合并的调试步骤，不是强制产品阶段。已知格式事实直接来自正式文件，不必每增一个目录就运行一次官方 GUI。

建议把下一目标改为：取得一组可归因的 PDF 正反对照。候选首组为 6.23：同一份六页合成文档，有有效书签为控制，移除书签为处理，再恢复控制。固定页面内容、上下文、程序版本及输出解析器；按依赖规则重算校验和。必须在官方报告中找到该文件和目标消息，完整保存额外消息。

这个设计仍是建议，尚未运行。若结构错误使 PDF 检查被跳过，只补足最早阻断的依赖；若存在固定非目标错误但目标消息已明确可归因，保留为研究性对照，不冒充合格序列。

6.22 的对照必须另选非豁免普通节点，不能使用说明函或申请表。字体对照应覆盖官方名单、常见别名、明确非标准字体及嵌入/未嵌入；不要只用 Base-14 生成器做自我证明。密码和权限限制作为交互对照，不强求一个样本只能出现一条官方消息。

这里的 control/baseline 是实验对照，不是受控词汇中的注册行为“基线”。不得为了让模型通过而自动填入 cnrat9 或 v4.0 baseline 豁免。

## 6. 下一阶段产品与校准双线并行

### 主线 A：安全的文件夹级只读工具

最低验收：一个目录中的 20 个合成 PDF 能完成递归扫描；一份文件损坏不终止整批；输出中文 HTML 和 JSON；定位文件/页/对象；展示未评估项和上下文限制；重复扫描无意外状态变化；所有输入及预先存在文件不被修改。20 是建议的首个验收批次，不是已有完成数量。

优先能力：密码/加密、结构可读性、页数和版本、书签存在性、动作与链接清单、附件与动态对象清单。字体、搜索性与跨文档语义在修复后按限定范围启用，不要将当前实现完整性的缺口藏在“规则覆盖 26/26”后面。

### 支线 B：官方差分校准

最低验收：同一程序版本、固定上下文的一组控制—处理—恢复控制，官方输出明确定位 PDF 且目标变化可解释。再扩展非豁免节点的 6.22 和字体边界。无需先扩展完整 Publisher；但没有官方实测的规则只能标记本地验证，不能标官方一致。

### 下一可交付：一项低风险副本修复

在保护边界修复、该项语义与适用性经过验证后，选一个小功能，例如非豁免、未签名普通 PDF 的线性化。只写独立输出；结构可打开；页数不变；全部页面同渲染器同参数前后比较；目标检查通过；签名文件必须阻断；失败输出不得冒充成功文件。

不要求其余 25 条 detector 都完成才允许研发这项功能，但绝不能省略全局输入保护和该功能自身验收。OCR、通用字体补嵌、页面缩放、内容删除和完整 Publisher 继续后置。

## 7. 本地 Codex 接管建议

建议转入本地 Windows 持久工作区做主开发，继续使用原 GitHub 仓库；这是工作方式调整，不是重写或迁库。Python 对象分析原型先保留，不急于改成 Rust/.NET 或冻结一个新的前端栈。

先从已审计的研究分支建立本地任务分支，核验 SHA 和 working tree；只克隆 main 不会得到当前研究实现。持久环境先完成可重复依赖安装、独立运行 CLI 和测试，然后接入 Codex。官方 GUI 自动化单独验证桌面会话、权限、区域设置和证据输出；本地 Codex 不天然保证能操作任何 Windows GUI。

本地文件操作不等于模型推理离线。`.gitignore` 只影响 Git 追踪，不是访问控制，也不阻止 Agent 读取文件。真实申报资料和私钥应放在任务允许范围之外，任务明确只读取合成或授权脱敏数据。管理员权限、防火墙更改、安装官方软件、网络访问均单独批准，不以“完整自动化”为由默认全权限。

首个 Codex 任务应是安全入口与可用性，不是继续扩展 Rung 规范：

1. 复现并修复 F01；补 CLI 级负面测试，而不是只测试 Observer。
2. 修复 F02 的读取根边界，补包外路径测试。
3. 实现 F04 的逐规则完成状态，补缺失依赖、提取失败和异常输入测试。
4. 修正 F03/F05/F08；以实际 PDF 集成样本补测。
5. 输出一次固定提交的完整测试结果和 20 文件目录演示。
6. 然后执行一组官方 PDF 正反对照，并提交阶段证据。

## 8. Agent loop 的约束

每轮只设一个可判定目标：假设、最小修改/实验、结果、反例、决定、下一步。原始输出保留，不能以修改 expected 值来消除未解释差异。

建议停止条件：同一阻断连续两次尝试没有新增信息时，暂停重复运行，检查最早未满足的依赖或切换本地最小复现；同一假设被证据否定后不得改名继续计作成功；达到本轮验收后停止扩大范围。

衡量进展用：用户任务是否完成、不可逆误改是否为零、规则评估完整性、独立样本误报/漏报、实际官方正反对照。不要使用提交数、运行数或文档数作为成熟度代理。
